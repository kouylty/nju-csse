### 一、项目概况

**项目背景。** 二手交易中，商品介绍、买卖沟通、交付约定和交易评价往往分散在不同位置，买家难以判断商品情况，卖家也难以持续掌握订单进度。直接付款还会带来“已经付款但尚未交付”的信任问题，一旦发生争议，双方缺少统一的交易依据。余闲二手交易系统围绕这些问题，将商品展示、站内沟通、下单付款、交付确认、双向评价及客服处理组织成连贯的业务流程。

**项目目标。** 系统以商品和订单为核心，为买家提供清楚的商品信息与交易保障，为卖家提供发布、库存和交易管理能力，为管理员提供审核、举报处理及第三方客服功能。通过保存下单时的商品内容和金额、明确订单状态转换、同步更新库存与模拟资金记录，使每笔交易都有明确的参与者、执行条件和处理结果，为后续设计、开发和测试建立统一依据。

**用户与权限。** 系统包含买家、卖家和管理员三类业务角色。买家与卖家由同一普通账号承担，用户购买他人商品时作为买家，发布和出售自己的商品时作为卖家；管理员权限单独授予，普通用户不能在注册时自行选择管理员身份。

| 用户角色 | 主要操作 | 权限边界 |
| --- | --- | --- |
| 买家 | 查询商品、站内沟通、下单及模拟付款、确认收货、申请退款或客服处理、评价卖家 | 不能购买自己的商品；不能操作他人订单；订单完成后才能评价 |
| 卖家 | 保存草稿、提交审核、修改价格和库存、下架商品、发货或交付服务、评价买家、查询成交统计 | 只能管理自己的商品；不能挪用已有订单占用的库存；不能自行恢复违规下架商品 |
| 管理员 | 审核商品、处理举报和纠纷、提供第三方客服、查看待办及操作记录 | 普通账号不能执行管理操作；有关退款和结算须关联具体订单并保留处理依据 |

**系统范围。** 本期覆盖物品和一次性交付服务的交易，支持商品草稿、审核发布、组合查询、站内聊天、同商品多件下单、模拟支付、邮寄或当面交付、自动确认、评价、统计和操作追溯。交易采用直接下单模式，不设置预约和购物车；支付、退款和结算使用系统内模拟记录，不接入真实支付机构；邮寄保留快递公司和单号，不自动追踪物流；服务不包含长期包月业务。并发处理以保证库存和状态正确为目标，售后纠纷及长期未履约问题由双方协商和客服处理。



### 二、整体业务分析

#### 2.1 主要业务流程

**商品准备与发布。** 卖家先保存草稿，再提交管理员审核。提交时须提供标题、至少一张图片、文字描述、类型、分类、库存和价格，并按交付方式填写邮费信息。价格大于零，提交审核时的库存为正整数；包邮商品邮费为零，不包邮商品填写正数邮费。审核通过后公开出售，驳回时向卖家说明原因，修改后可重新提交。已发布商品调整价格、邮费或库存可直接生效，修改图片、描述、类型或分类须重新审核，审核期间停止接新单。

**商品查找与沟通。** 买家可组合使用关键词、分类、价格区间、物品或服务类型及在售状态筛选商品。商品详情展示图片、描述、库存、价格、邮费、卖家和历史买家评价，没有评价时显示“暂无评价”。买家在下单前即可通过站内聊天询问商品情况和交付方式，聊天记录与有关商品或交易保持关联。

**下单与金额确定。** 一笔订单购买一种商品，允许购买多件同款商品。数量由买家手动输入，默认值为 1，必须为不超过当前可用库存的正整数。订单总价按照“下单单价×购买数量＋本单邮费”计算，邮费按订单收取一次。系统创建订单时同时占用对应数量的库存，并保存当时的商品内容、数量、单价、邮费和总价。之后商品改价或下架均不改变该订单的约定。

**模拟付款与交付。** 买家完成模拟付款后，系统先将交易款记录为平台暂存，订单进入待发货或服务待履约阶段。邮寄订单由买家填写收件人、电话和地址，卖家发货时填写快递公司和单号；当面交付由双方通过聊天约定地点，卖家完成交付后标记已交付。服务订单在付款后约定履约时间，卖家依次标记开始服务和服务已交付，页面使用“交付”“确认完成”等对应术语。

**确认完成与评价。** 买家可以在交付后主动确认，也可以由系统在七天后自动确认，订单展示具体自动确认时间。确认完成后，平台生成卖家的模拟结算记录，双方可各自提交一次一至五星及文字评价。买家的评价同时显示在商品页面和卖家收到的评价中，卖家的评价显示在买家评价页面。

**取消与退款。** 买家可在付款前取消订单，十五分钟内未付款的订单自动关闭并释放库存。已付款但尚未发货的物品、尚未开始的服务，可以由任意一方提出取消；协商期间暂停履约和结算，另一方同意后全额模拟退款、关闭订单并释放对应库存，邮费一并退还。拒绝或撤回申请后恢复原待履约阶段。库存释放只恢复数量，不改变商品原有的审核或下架状态。

**举报与纠纷处理。** 商品页、聊天和订单分别提供商品举报、聊天举报和纠纷处理入口。管理员可驳回商品举报、要求整改或违规下架，并记录理由。已发货退货、服务开始后取消、长期未发货或申请无人回应等问题，由双方协商和客服介入处理；系统保存处理意见并向双方反馈。订单进入纠纷处理后暂停自动确认和结算，退款金额、运费承担及后续履约按具体协商结果执行。

**查询统计与管理。** 卖家按时间查询自己的完成订单数、成交金额及模拟到账金额，退款关闭的订单不计入成交统计；管理员查看待审核商品、待处理举报及待处理纠纷的数量。改价、审核、下架、订单状态变化、退款、结算和客服处理保留操作记录，支持按时间、操作人、商品号或订单号查询。

#### 2.2 主要数据之间的关系

业务数据围绕订单组织。用户通过商品建立买卖关系，订单保存一次交易的具体约定，付款、退款、结算和评价记录进一步描述该笔交易的执行过程；聊天、举报、纠纷和日志为沟通与管理提供依据。商品当前信息与订单历史信息分别保存，使商品后续修改不会改变已经成立的交易。

| 数据对象 | 主要内容 | 关联关系与约束 |
| --- | --- | --- |
| 用户 | 账号、身份及权限 | 账号名唯一；同一普通账号可作为不同订单的买家或卖家 |
| 商品 | 卖家、图片、描述、类型、分类、价格、库存、邮费及审核状态 | 商品归属卖家；一个商品可对应多笔订单；有订单的商品保留历史资料 |
| 订单 | 订单号、双方、商品内容快照、数量、单价、邮费、总价、状态及相关时间 | 订单号唯一；一笔订单关联一个买家、一个卖家和一种商品 |
| 模拟资金记录 | 付款、平台暂存、退款及结算的金额和结果 | 每项记录关联具体订单；重复操作不重复付款、退款或结算 |
| 交付信息 | 收件资料、快递公司和单号，或当面交付、服务履约信息 | 关联订单；不同交付方式使用对应字段和起算时间 |
| 聊天与评价 | 参与者、消息、评分、评价文字及所属交易 | 聊天关联有关商品或交易；同一订单同一评价人至多一条评价 |
| 举报与纠纷 | 对象、申请人、原因、图片、受理情况、处理意见及结果 | 举报关联商品或聊天，纠纷关联订单，处理结果保留业务依据 |
| 操作日志 | 操作人、时间、操作内容、变更前后值或状态 | 关联有关用户、商品或订单，支持业务过程追溯 |

**数量同步。** 下单按购买数量占用库存，付款前取消、未付款关闭和交付前协商退款按原占用数量释放库存，每次占用或释放只生效一次。卖家调整可售库存时不能移走已为订单保留的数量。商品售罄反映可用数量为零，与“下架”“待审核”等管理状态分别判断；释放数量不会让一个已下架商品重新上架。

**金额同步。** 模拟付款金额等于订单保存的总价，交付前取消退还该订单全部商品金额和邮费，确认完成后结算该订单的平台暂存金额。模拟记录与订单、库存的关联更新作为同一项业务操作完成，内部写入失败时保留原状态，避免出现只扣库存而没有订单，或已经退款却重复释放库存的结果。

**唯一性与重复购买。** 同一买家可以多次购买同一商品，但同时最多保留一笔该商品的待付款订单；付款或关闭后可以再次主动下单。一次下单的重复点击或请求重试按同一提交标识处理，即使原订单后来已经付款，重试旧请求也不能被解释为新的购买。

#### 2.3 业务状态和状态转换

**商品状态。** 商品的生命周期以草稿、待审核、审核驳回、已发布、主动下架和违规下架为主要阶段。状态决定谁能够操作商品、买家是否能够购买，以及修改后是否需要再次审核。

| 当前状态 | 触发条件与允许的转换 | 主要限制 |
| --- | --- | --- |
| 草稿 | 卖家填写资料并通过校验后提交为待审核 | 仅所属卖家可见，不能直接出售 |
| 待审核 | 管理员通过后转为已发布，拒绝后转为审核驳回 | 不接新单，卖家不能自行审核通过 |
| 审核驳回 | 卖家根据原因修改后重新提交待审核 | 不能跳过审核直接发布 |
| 已发布 | 调整价格、邮费或可售库存；关键内容修改后转待审核；卖家主动下架或管理员违规下架 | 不能修改历史订单约定，不能挪用订单占用库存 |
| 主动下架 | 卖家重新提交审核，通过后恢复发布 | 库存恢复不自动上架 |
| 违规下架 | 根据管理员处理意见开展整改 | 卖家不能自行恢复出售 |

**订单状态。** 实物交易的正常路径为“待付款→待发货→待收货→已完成”，服务交易在付款后经历“待开始→服务进行中→已交付待确认→已完成”。取消协商、纠纷处理和关闭构成正常流程之外的处理分支。

| 当前状态 | 触发条件与允许的转换 | 主要限制 |
| --- | --- | --- |
| 待付款 | 模拟付款成功后进入待发货或服务待开始；主动取消或十五分钟未付款后关闭 | 未付款不能发货或开始服务；关闭须释放对应库存 |
| 待发货／服务待开始 | 发货或开始服务；双方均可提出取消并进入取消协商 | 不得在取消协商期间继续发货、开始服务或结算 |
| 服务进行中 | 卖家完成工作后标记已交付待确认 | 取消须协商或由客服介入，不直接套用服务开始前全额退款 |
| 取消协商中 | 同意后全额模拟退款并关闭；拒绝或撤回后恢复原待履约阶段 | 长期未回应不自动同意、退款或判责 |
| 待收货／已交付待确认 | 买家主动确认或交付七天后自动完成；申请并进入纠纷处理 | 未解决纠纷时暂停自动确认和结算 |
| 纠纷处理中 | 客服记录并执行双方协商形成的处理结果 | 不预设退款比例、自动结案或自动恢复计时 |
| 已完成 | 生成模拟结算记录，允许双方评价；售后交由协商及客服处理 | 不能重复结算，同一方不能重复评价 |
| 已关闭 | 保留订单、退款及相关处理记录 | 不能重新付款或发货；再次购买须创建新订单 |

**并发和旧页面。** 两名买家同时争抢最后一件商品时，系统通过简单并发控制保证最多一笔订单成功，失败的一方收到库存不足提示。旧页面提交时重新检查商品状态、数量、单价和邮费；商品下架或库存不足时拒绝下单，金额变化时提示刷新并重新确认。付款与关闭、取消与发货、手动与自动确认等冲突，以先成功完成的合法状态变更为准，后续操作基于最新状态判断，不重复产生库存和模拟资金变化。



### 三、实验总结

#### 3.1 访谈中的问题与解决方法

第一次访谈先围绕角色、商品、付款、交付和评价建立整体认识，形成交易主流程；后续跟进再围绕实际操作补充账号复用、草稿审核、库存占用、自动收货、退款协商和服务交付等规则。这样的推进顺序使访谈从使用者容易描述的场景出发，再逐步进入状态、权限和边界，避免在开头就用大量技术问题打断业务表达。

访谈中最有代表性的问题是自然语言的歧义。“退货”在发货前实际表示取消交易并退款，而服务已经开始后的取消又不能直接套用同一规则；“一笔订单可以买好多件同样的商品”与末尾“单件直接下单”的总结也存在冲突。在人工审查中明确了一单一种商品、同款可购买多件的规则，并补齐数量输入、库存上限和计价公式，使业务含义能够直接对应界面、数据和验收用例。

#### 3.2 需求整理与一致性分析

本次整理将口语化访谈转化为具有稳定编号和统一字段的需求条目，并把每项关键规则关联到访谈或人工审查记录。需求分析的重点是厘清同一操作对多项数据的影响。例如，允许多件购买后，数量上限、订单总价、库存占用、退款释放和成交统计都需要同步调整；修改支付方式后，付款、平台暂存、退款、结算及到账统计也必须统一为模拟金额。通过检查这些关联，最终文档形成了连贯的业务规则。

同时将正常流程与异常边界一起整理。下单不仅描述“生成订单”，还规定不能购买自己的商品、不能超库存、不能重复形成待付款订单等等。确认完成不仅描述“给卖家结算”，还考虑自动确认、人工确认和纠纷暂停之间的关系。这样的表达让后续开发能够明确操作条件，也让测试能够从需求直接构造成功、失败和冲突场景。

#### 3.3 人工审查与修改成果

人工审查围绕课程实验的实际规模和业务表达开展，重点解决初稿中的范围不清、规则未定和验收标准缺失。六项代表性审查分别记录在 REV-001 至 REV-006 中，修改结果同步落实到关联需求、业务状态表及需求统计。

| 审查记录 | 核对重点 | 处理结果 |
| --- | --- | --- |
| REV-001 | 单件与多件购买存在歧义，数量和计费规则不完整 | 确定同商品多件下单、默认数量 1、库存上限和按单邮费，并同步库存与订单快照 |
| REV-002 | 支付接入方式及真实渠道异常扩大了实现范围 | 明确模拟支付、退款和结算，保留平台暂存及完成后结算的业务关系 |
| REV-003 | 主动复购、重复点击与并发购买未充分区分 | 设置同买家同商品最多一笔待付款订单，识别同次请求重试，采用并发控制 |
| REV-004 | 售后与纠纷处理缺少明确的范围边界 | 交由双方协商和客服处理，保存意见与结果，不设固定退款政策或自动判责 |
| REV-005 | 长期未履约及申请未回应的处理方式不明确 | 保留客服处理路径和交付后自动确认，不增加这些等待阶段的自动化处理 |

这轮审查将课程实验的实现重点集中到商品管理、订单履约和数据一致性上。模拟支付保留了交易中的资金去向，简单并发控制覆盖了真实的库存竞争，客服处理承接了难以统一自动化的争议情形。需求因此既能表达完整的主要交易过程，又有明确的实现范围和可检查的验收条件。

#### 3.4 AI 的作用与局限

AI 在本实验中承担了材料整理和初稿结构化工作，将两轮访谈中的分散描述组织为需求条目，并补全来源、前置条件、异常边界和验收方法的表达。它还帮助识别了购买数量的矛盾、支付接入方式未定、售后规则不明确和性能目标缺失等问题，使人工审查能够集中处理影响开发的关键决策。

人工判断决定了最终需求的取舍。对于支付和并发，课程实验采用模拟支付与简单并发控制；对于纠纷和未履约问题，明确交给协商与客服；对于性能，结合实验规模制定可复现的目标。这个过程说明，AI 能高效组织信息、检查关联并形成初稿，而项目范围、业务约定和验收目标需要由需求分析人员结合实际场景确定。
